# Техническое задание на ИТ-решение «INDUSTRIA TWIN»

Цифровой двойник сборочного производства насосов и интерактивный 3D-тур по производству.
Версия документа 1.1 (вторая итерация: CRN и парное сравнение, отказы оборудования, советник по ресурсам, кейсы тура, экспорт). Документ подготовлен для двухэтапного студенческого хакатона «Цифровой двойник предприятия и 3D-туры по производству» и описывает реализованный прототип; все утверждения сверены с исходным кодом репозитория.

> **Данные синтетические.** Предприятие условное; все производственные параметры придуманы для демонстрации и не являются реальными показателями. Результаты моделирования рассчитываются симулятором.

## 1. Введение

### 1.1. Назначение документа
Документ фиксирует требования, архитектуру, модели процессов и данных, интерфейсы, модель симуляции, устройство 3D-тура, критерии приёмки и план проверок прототипа INDUSTRIA TWIN.

### 1.2. Область применения
Прототип предназначен для демонстрации подхода «процесс → сценарий → метрики → 3D-тур» на модели одного цеха. Промышленная эксплуатация без калибровки модели по фактическим данным не предполагается.

### 1.3. Термины

| Термин | Определение |
|---|---|
| Участок (station) | Производственная зона с пулом однотипных ресурсов; идентификатор `stationId` (например, `st-testing`) |
| Задание / изделие | Один насос, проходящий маршрут; в модели — единица потока |
| Вместимость (capacity) | Число параллельных единиц ресурса участка (станков, постов, стендов) |
| Горизонт | Длительность моделирования, мин |
| Репликация | Независимый прогон модели с собственным seed |
| Прогон (run) | Набор из R репликаций одного сценария, сохранённый в БД |
| НЗП | Незавершённое производство — изделия в очередях и в обработке на конец горизонта |
| Узкое место | Участок с наивысшим статусом загрузки (правила — раздел 15.6) |
| ДСМ | Дискретно-событийное моделирование |
| POI | Точка интереса 3D-тура (`poiId`) |

## 2. Контекст предприятия

Условное предприятие «Насосный завод „Industria“» (`factory-pump-01`) изготавливает и собирает центробежные насосы. Процесс `process-pump-assembly` включает шесть участков:

| Код | stationId | Участок | Зона | Ресурс (базовый сценарий) |
|---|---|---|---|---|
| A1 | `st-receiving` | Склад входящих компонентов | Зона A — Приёмка | Кладовщики-комплектовщики, 1 чел. |
| B1 | `st-machining` | Механическая обработка | Зона B — Механообработка | Обрабатывающие центры с ЧПУ, 3 станка |
| C1 | `st-assembly` | Сборочный участок | Зона C — Сборка | Сборочные посты, 2 поста |
| D1 | `st-testing` | Испытания и ОТК | Зона D — Испытания | Испытательные стенды, 1 стенд |
| D2 | `st-rework` | Устранение дефектов | Зона D — Испытания | Пост доработки, 1 пост |
| E1 | `st-packing` | Упаковка и отгрузка | Зона E — Отгрузка | Линия упаковки, 1 линия |

Основной маршрут: A1 → B1 → C1 → D1 → E1. После испытаний D1 выполняется контроль: годное изделие идёт на E1, изделие с дефектом — на D2 и повторно на D1; после исчерпания лимита доработок изделие списывается.

Рабочий день моделируется горизонтом 960 мин (две 8-часовые смены). Источник параметров — `src/domain/model/demoData.ts`, обоснование допущений — раздел 10 и страница `/documentation`.

## 3. Проблема

Изменение на одном участке (рост спроса, добавление поста, повышение качества) влияет на очереди и загрузку соседних участков. Руководителю нужно:
- видеть, где возникают задержки и перегрузка ресурсов;
- проверять гипотезы до их внедрения: как изменение повлияет на время цикла, выпуск, загрузку и стоимость;
- сравнивать альтернативы по показателям с учётом случайной изменчивости.

Внешней аудитории (посетителям, партнёрам, студентам, новым сотрудникам) нужен понятный визуальный рассказ о производстве, в котором показатели не придуманы, а связаны с моделью процесса.

## 4. Цель и задачи

**Цель:** прототип цифрового двойника цеха и браузерного 3D-тура, использующих одну логическую модель участков, ресурсов и метрик.

**Задачи:**
1. Описать процесс, ресурсы, время и стоимость операций в единой модели с стабильными идентификаторами.
2. Реализовать дискретно-событийный симулятор с воспроизводимыми репликациями.
3. Реализовать поиск узких мест и сравнение сценариев «до/после» со статистической оценкой различимости.
4. Реализовать редактирование, сохранение и запуск сценариев.
5. Реализовать дашборд, мнемосхему и интерактивный 3D-тур с точками интереса и воспроизведением прогона.
6. Обеспечить базовую авторизацию, ролевое разграничение и минимизацию персональных данных.
7. Подготовить документацию первого этапа и тесты.

## 6. Границы системы

**Входит:** модель одного цеха; ДСМ-движок; хранение сценариев и результатов в SQLite; веб-интерфейс (дашборд, мнемосхема, студия сценариев, сравнение, 3D-тур, документация, администрирование); REST-подобный JSON API; аутентификация по логину и паролю.

**Не входит:** интеграции с ERP, MES, 1С и другими внешними системами; загрузка фактических данных; управление реальным оборудованием; планирование производства; переналадки, поломки, графики смен и перерывов; мультизаводская модель; регистрация пользователей через интерфейс; хранение медиафайлов (используются процедурные визуализации).

## 10. Ограничения и допущения

### 10.1. Технические ограничения (из задания)
Нет интеграций с ERP/MES/1С; базовая авторизация; веб-интерфейс для трёх классов устройств; учёт 152-ФЗ; WebGL/Three.js; синтетические данные.

### 10.2. Допущения модели
- Поток заданий пуассоновский (или равномерный — параметр); все изделия однотипны; дисциплина очередей FIFO.
- Длительности операций — треугольные распределения (в базовом сценарии); поддерживаются также фиксированное, экспоненциальное, равномерное, усечённое нормальное.
- Отказы оборудования задаются на участок (MTBF, MTTR): пуассоновский поток отказов с интенсивностью вместимость/MTBF, экспоненциальный ремонт, неупреждающая модель (единица уходит в ремонт после завершения текущей операции). Нет переналадок, перерывов, графиков смен, транспортного времени между участками и ограничений буферов.
- Дефект выявляется только на испытаниях D1; вероятность брака при повторных испытаниях задаётся отдельно; лимит доработок — 2 в базовом сценарии.
- Система стартует пустой; период разгона по умолчанию не исключается (параметр `warmupMin` = 0) и может быть исключён в сценарии — тогда статистика собирается после разгона.
- Ресурсы оплачиваются за доступность (вместимость × горизонт × ставка), а не за занятость.

### 10.4. Ограничения реализации
- Ограничитель частоты хранится в памяти одного процесса Node.js (для кластера требуется внешнее хранилище).
- Моделирование выполняется синхронно в обработчике запроса (прогон базового сценария занимает миллисекунды); очередь фоновых задач не реализована.
- Журнал событий сохраняется только для репликации №1 и не более 60 000 событий.
- Статус прогона `failed` предусмотрен схемой, но неуспешные прогоны не сохраняются — ошибка возвращается клиенту.
- Медиа точек интереса — процедурные ракурсы сцены; внешние фото/видео не загружаются.

## 15. Модель симуляции

### 15.1. Тип модели
Дискретно-событийная модель сети очередей с ограниченными многоканальными узлами, контуром доработки и горизонтом моделирования. Модуль `src/domain/simulation` не зависит от UI, React и БД.

### 15.2. Календарь и события
Календарь — двоичная min-куча с порядком «время → приоритет → порядковый номер постановки». Приоритеты при совпадении времени: `PROCESS_FINISH` (0) → `ARRIVAL` (1) → `HORIZON_END` (9).

| Событие | Тип | Смысл |
|---|---|---|
| `ARRIVAL` | календарное | Поступление задания; планирование следующего прихода |
| `QUEUE_ENTER` | мгновенное | Постановка изделия в очередь участка |
| `PROCESS_START` | мгновенное | Начало операции при свободной единице ресурса; списание расходников |
| `PROCESS_FINISH` | календарное | Окончание операции; освобождение ресурса и взятие следующего задания |
| `QUALITY_CHECK` | мгновенное | Контроль после испытаний, признак дефекта |
| `REWORK` | мгновенное | Направление на участок доработки |
| `SCRAP` | мгновенное | Списание после исчерпания лимита доработок |
| `DEPARTURE` | мгновенное | Отгрузка годного изделия |
| `HORIZON_END` | календарное | Окончание моделирования; фиксация НЗП |
| `FAILURE` / `REPAIR_END` | календарные | Отказ единицы ресурса участка / окончание ремонта (в журнале — `BREAKDOWN` / `REPAIR`) |

### 15.3. Случайность и воспроизводимость
ГПСЧ sfc32 с инициализацией splitmix32; репликация 0 использует базовый seed, репликация i — `deriveSeed(seed, i)` (31 бит). С версии 1.1.0 применяются общие случайные числа: каждый источник случайности получает свой поток `streamSeed(seed, поток, адрес)`, поэтому в сценариях с одинаковым seed одно изделие получает одинаковые длительности операций и исходы контроля. Длительности ограничиваются снизу нулём; некорректные параметры отклоняются до запуска (`validateConfig`).

### 15.4. Ограничения безопасности
`ENGINE_LIMITS`: горизонт ≤ 10 080 мин, вместимость ≤ 50, интенсивность ≤ 120 шт./ч, циклов доработки ≤ 5, событий ≤ 2 000 000, записываемых событий ≤ 60 000; репликаций ≤ 30.

### 15.5. Показатели
Загрузка участка = интеграл числа занятых единиц по времени / (вместимость × горизонт). Средняя загрузка = Σ интервалов занятости / Σ (вместимость × горизонт). Время цикла = выход − поступление (только завершённые изделия) = ожидание + обработка. Доля брака = выявленные дефекты / выполненные проверки. Стоимость = ресурсы (вместимость × горизонт, ч × ставка) + расходники (начатые операции × расходы) + компоненты (запущенные задания × комплект) + постоянные расходы; стоимость единицы = стоимость / выпуск, `null` при нулевом выпуске. Полный каталог — `src/domain/model/metrics.ts` и `/documentation`.

### 15.6. Узкие места
Статус участка определяется по эффективной загрузке (занятость + доля времени в ремонте): «перегрузка» при ≥ 90% или очереди на конец горизонта ≥ 2 × вместимость (и ≥ 3); «высокая загрузка» при ≥ 75%; иначе «норма». Ранжирование: статус → загрузка → среднее ожидание. Узкое место — первый участок рейтинга со статусом не «норма».

### 15.7. Сравнение
Средние по репликациям. Для прогонов движка ≥ 1.1.0 с одинаковым seed и числом репликаций — парное сравнение: 95% ДИ по разностям внутри пар репликаций; иначе — 95% ДИ разности средних по Уэлчу. Разность различима, если интервал не содержит ноль; при n < 2 различимость не оценивается. Советник дополнительно считает изменения меньше 1% практически несущественными. Вердикт учитывает направление улучшения показателя. Вывод относится к модели и не доказывает причинно-следственную связь на реальном производстве.

- **Сцена:** процедурная геометрия без внешних файлов: пол, стены, колонны, напольная разметка зон с кодами, стеллажи с паллетами, станки с ЧПУ, сборочные посты с порталом и талью, испытательные стенды с баком и трубопроводом, пост доработки, упаковочная линия, роликовые конвейеры, насосы, сигнальные колонны.
- **Компоненты:** `FactoryCanvas`, `FactoryEnvironment`, `FactoryLayout`, `StationAnchor`, `EquipmentModel`, `ConveyorSystem`, `ProductionItems` (ProductionItem), `FactoryCameraController`, `FactoryTour` (TourNavigation), `MetricsOverlay`/POI, `StationHighlight`, `SceneQualityController`, `FactoryPlan2D`.
- **Система координат:** метры, Y — вверх, X — по потоку. Камеры: `cam-overview`, `cam-top` и по одной на участок.
- **Режим «Экскурсия»:** 7 остановок маршрута `tour-main`; показатели — средние выбранного прогона.
- **Режим «Воспроизведение»:** кадры с шагом 5 мин из журнала событий репликации №1; очереди и занятость оборудования соответствуют кадру. Единицы в ремонте обозначены ограждением и выноской «Ремонт». Анимации шпинделей, стрелок и обмотчика включаются только для занятого оборудования.
- **Связь с аналитикой:** каждый объект участка привязан к `stationId`; карточки не содержат собственных данных.
- **Резервный режим:** при отсутствии или потере WebGL — 2D-план с теми же участками, маршрутом и метриками.

## 17. Критерии приёмки

Полный перечень — [ACCEPTANCE_CRITERIA.md](ACCEPTANCE_CRITERIA.md) (AC-01…AC-26 и критерии готовности Q-01…Q-17). Ключевые: вход и роли работают; симуляция выполняется и воспроизводима; сценарии сохраняются; сравнение показывает результаты; 3D-сцена загружается и связана с теми же участками; тесты, typecheck и production build проходят; демонстрация выполняется без ручного исправления данных.

## 18. План тестирования

Полный план — [TEST_PLAN.md](TEST_PLAN.md). Уровни: модульные тесты движка и аналитики (инварианты сохранения изделий, загрузки 0..100%, неотрицательных длительностей, вместимости, порядка событий), интеграционные тесты API на изолированной БД, E2E Playwright (desktop, tablet, mobile, без WebGL), ручные проверки производительности 3D и демонстрации.

## 19. Риски

| Риск | Влияние | Мера |
|---|---|---|
| Модель не откалибрована по реальным данным | Неверные управленческие выводы | Явная маркировка синтетических данных, раздел ограничений, формулировки без причинных утверждений |
| Высокая дисперсия результатов при малом числе репликаций | Ложные выводы о различиях | ДИ и проверка различимости по Уэлчу; по умолчанию 20 репликаций |
| Производительность 3D на слабых устройствах | Неудобство тура | Адаптивное качество, instancing, ограничение DPR, 2D-план |
| Отсутствие WebGL | Нет 3D | Резервный 2D-план |
| Злоупотребление запуском тяжёлых прогонов | Нагрузка на сервер | Лимиты движка, проверка тяжести прогона, ограничение частоты |
| Ограничитель частоты в памяти | Не работает в кластере | Зафиксировано как ограничение; для production — внешнее хранилище |
| Утечка демо-паролей | Несанкционированный доступ к демо-стенду | Пароли переопределяются переменными окружения `DEMO_*_PASSWORD`; `SESSION_SECRET` уникален для установки |
| Формальное соответствие 152-ФЗ | Юридические риски | Технические меры минимизации; организационные меры оператора вне рамок прототипа |

## 20. Сценарий демонстрации

Подробно — [DEMO_SCRIPT.md](DEMO_SCRIPT.md) (5–7 минут, все числа — из фактических расчётов):
1. 3D-тур: общий план цеха.
2. Дашборд: KPI базового сценария.
3. Мнемосхема исходного процесса.
4. Запуск базового сценария в студии сценариев.
5. Выявление перегруженного участка (блок «Узкое место»).
6. Переход к участку в 3D.
7. Очередь и метрики участка в сцене и на панели.
8. Возврат в студию сценариев.
9. Добавление ресурса или изменение параметра.
10. Запуск нового сценария.
11. Сравнение результатов с базовым.
12. Изменившееся состояние 3D-цеха (число постов, очереди, статус).
13. Какое управленческое решение поддерживает система и с какими оговорками.
